# 한컷점검 — 보안검색 X-ray 판독 운영점 (1인)

2026-09-27 기준. 범위 #12, 과제 정의 #16, 최종 정리 D11. 이전 계획은 `docs/archive-*/`.

## 한 문장

보안검색 X-ray 사진을 **놓침률 상한 아래에서 자동통과 / 재검 / 자동적발** 세 구간으로 나눠,
판독관이 직접 봐야 할 사진을 몇 %까지 줄일 수 있는지 정한다.

## 정답이 전부 데이터 안에 있다

놓침률·재검률·오경보율·자동 처리율은 **PIDray 라벨만으로 계산된다.** 사람의 응답이 필요 없다.
인간 판독관 정확도 80~90%(EU JRC)는 문헌에서 인용하는 **비교 좌표**일 뿐 모델의 입력이 아니다.

이전 설계(D10)는 판독관을 시뮬레이션해야 했고, 그래서 "사람 일을 덜어준다"는 결론의 근거가 데이터 밖에 있었다.
D11 에서 그 구조를 없앴다.

## 품목 단위 이진 정의

받을 수 있는 PIDray 47,677장은 전부 위해물품이 든 사진이라 "빈 가방을 자동 통과"는 측정할 수 없다.
대신 **품목 단위**로 본다.

> 품목 c 에 대해 — 그 품목이 든 가방이 양성, 안 든 가방이 음성.
> 놓침 = 품목 c 를 놓침. `y_true=1` 은 "품목 c 있음", `score` 는 `p(품목 c 있음)`.

품목마다 양성과 음성이 모두 생긴다. 12종이면 이진 문제 12개다.

## 무엇이 기여인가

탐지도 분류도 포화다. PIDray 의 다중 라벨 분류·검출은 이미 논문의 공식 벤치마크다.
**새 탐지기를 만들지 않는다.** 사전학습 검출기를 쓴다.

비어 있는 것은 **"놓침률을 묶었을 때 얼마나 자동화되는가"** 이고,
여기에 PIDray 만 줄 수 있는 두 축이 붙는다.

| 축 | 질문 | 데이터 근거 |
|---|---|---|
| ~~장비~~ | ~~장비가 바뀌면 임계값을 다시 잡아야 하나~~ | **취소 — 데이터에 장비 정보가 없다 (D12)** |
| **난이도** | 겹친 것과 숨긴 것 중 무엇이 운영점을 더 무너뜨리나 | easy 9,482 / hard 3,733 / hidden 5,005 |

난이도 축은 이미 데이터 안에 있어 추가 수집이나 가정이 필요 없다.
실측해 보니 easy 와 hidden 은 **이미지당 정확히 1종**이고 hard 만 2.08종이다.
hard 는 겹쳐서, hidden 은 숨겨서 어렵다 — 서로 다른 종류의 어려움이라 비교할 값어치가 있다.

## 완료 기준

품목별·난이도별 놓침률·재검률·오경보율·자동 처리율을 **분모와 함께** 보고한다.

측정 한계는 미리 쟀다. 주 격자는 **5·2·1%** 이고 0.5% 는 6종만, 0.1% 는 불가다(D12).
작은 표본의 1% 상한을 현장 보장치로 주장하지 않는다.

## 하지 않을 주장

**새 탐지기를 발명했다고 말하지 않는다.** 탐지는 기존 연구가 충분하고, 그걸 쓴다.

**TSA/ECAC 의 요구 수치를 단정하지 않는다.** 보안민감정보로 비공개다. 상한을 파라미터로 두고 스윕한다.

**실제 공항 운영에 쓸 수 있다고 말하지 않는다.** 공개 벤치마크 위의 분석이다.
PIDray 는 공항·지하철·기차역에서 수집됐다. 공항 전용이라고 말하지 않는다.

## 현재 구현

`ml/hancut/eval/zones.py`(3구간 판정·임계값 탐색)가 **이 과제의 중심**이다. E2·E3·E4·E5 가 전부 여기를 쓴다.
`eval/cli.py`, `data/subset.py`, 판정 API 골격, Flutter 앱 골격도 그대로 쓴다.

새로 필요한 것은 라벨 로더, 검출기 연결, 박스→이미지 점수 변환, 장비·난이도별 비교 스크립트다.

코드의 `facility`·`compliant` 식별자는 소방시설 시절 이름이다. #13 에서 정리한다.
데이터·가중치·키는 Git 에 넣지 않는다.
